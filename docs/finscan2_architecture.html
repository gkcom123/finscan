FinScan2 Architecture

A controlled financial-document pipeline: read a filing, resolve a reviewed mapping, validate the result, and write a traceable copy of the Excel model.

Current: FinScan2 is a local CLI application. It has no HTTP API, Teams bot, Foundry agent, or Blob Storage integration today.
Target: Deploy one FinScan2 worker image with a small asynchronous job API. Foundry is optional and only provides a Teams-facing conversational interface.

Executive Summary

flowchart LR Analyst[Analyst] --> Client[Teams, UI, or scheduler] Client --> API[FinScan2 job API] API --> Queue[Durable job queue] Queue --> Worker[FinScan2 worker job] Worker --> Artifacts[Workbook, audit JSON, report] Foundry[Optional Foundry agent] --> API

The worker is the only component that parses financial filings, resolves values, validates safety controls, and writes workbooks. The API submits jobs and publishes their status; it does not execute a long PDF/Excel run inside an HTTP request.

Identity and Boundaries

flowchart LR Client[Approved client] -->|HTTPS + Entra token| API[FinScan2 API] API -->|queue message| Worker[FinScan2 worker] API -->|managed identity| Blob[(Blob Storage)] Worker -->|managed identity| Blob Worker -->|managed identity| KV[Key Vault] Worker -->|managed identity| AOAI[Azure OpenAI]

The API is the only public boundary. Foundry, Teams, an internal UI, and schedulers call the API with Entra ID. The worker receives only queued jobs and has no need to accept public HTTP traffic.

Processing Pipeline

flowchart LR PDF[PDF bytes] --> Hash[SHA-256] Hash --> Cache{Matching cached parse?} Cache -->|yes| Doc[PdfDoc] Cache -->|no| Text[Text and table extraction] Text --> OCR[OCR fallback] OCR --> Statements[Statement and note parsing] Statements --> Doc Doc --> Resolve[Resolve reviewed mapping] Resolve --> Check[Period, coverage, and adjustment checks] Check --> Write[Copy and update workbook] Write --> Result[Workbook plus audit artifacts]

The normal run command reads company filings, learns a mapping only when none exists, and then applies the approved mapping. read, learn, and apply remain available as diagnostic stages.

Optional Model and Vision Path

flowchart LR Mapping{Vision reader enabled?} -->|no| Rule[Rule-based parser] Mapping -->|yes| Image[Render table page] Image --> Model[Configured vision model] Model --> Verify[Verify figures against PDF text] Rule --> PDFDoc[Common PdfDoc contract] Verify --> PDFDoc

Rule-based parsing is the default. A company mapping can opt into the vision reader only for filings whose table layout cannot be read reliably from text. Vision output is cached and figures that cannot be verified against the text layer must not be written automatically.

“Latest” must mean the newest approved financial period, not the most recently uploaded file. Store company, period end, filing type, approval state, and source identifier in a manifest or job/input record.

Foundry is optional. It is useful for a Teams conversation, but it must relay the API's audited figures and warnings rather than calculate or reinterpret financial values.

Deployment Strategy

Phase A: Cloud batch proof

  1. Build a FinScan2 worker image.
  2. Run it as a Container Apps Job for a known company.
  3. Save the workbook and full audit set to Blob Storage.
  4. Compare cloud results with local FinScan2 audits.

Phase B: Asynchronous service

  1. Add the Job API, Service Bus, and durable job state.
  2. Use Entra ID, managed identity, Key Vault, and Application Insights.
  3. Add idempotency, alerts, retention, and operational dashboards.

Phase C: Analyst experience

  1. Add an operations UI or Power Automate trigger.
  2. Add Foundry and Teams only when natural-language interaction is valuable.
  3. Pilot selected companies before wider rollout.

Operations and Security

  • Use managed identities and least-privilege RBAC for API, worker, and CI.
  • Require Entra ID at the API boundary; use API Management or Front Door for public access.
  • Use time-limited output download URLs and never expose public Blob containers.
  • Correlate every API request and worker execution with one job ID.
  • Record filing hash, mapping/parser/model versions, timings, model calls, and final result.
  • Run workers asynchronously and scale them to zero between filings.

Open Implementation Work

  • FinScan2-specific FastAPI Job API and worker launcher.
  • Service Bus, Blob input resolver, artifact publisher, and durable job state.
  • FinScan2-specific Azure OpenAI managed-identity client.
  • Entra ID authorization, Bicep, CI/CD workflow, production runbook, and alerts.
  • Foundry/Teams OpenAPI contract only if that analyst interface is required.
